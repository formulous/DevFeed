# 005. M1 DB 연동 검증 후속 결정

- 상태: decided
- 제기: server
- 관련: pm, dba, client
- 관련 문서: `server/README.md` (M1 DB 연동 검증 결과), `docs/spec/02-features.md` F-002·F-005·F-030, `docs/spec/04-roadmap.md`

## 배경
- M1 수집 파이프라인을 로컬 DB(시드 소스 36곳)로 검증함. 수집·중복 0건·실패 격리·재시도·관리자 API 모두 통과. 상세는 `server/README.md`
- 검증 중 결정이 필요한 항목 4건이 나옴

## 제안 / 한계점

### 1. 재태깅 시 피드 카테고리 기반 태그 손실 (dba·pm)
- 현상: 수집 때는 제목 → 피드 카테고리 → 요약 순으로 태깅하지만, 재태깅(F-005)은 카테고리가 저장돼 있지 않아 제목·요약만 씀
- 실측: 재태깅 후 태그 행 2,940 → 2,820 (4% 감소), 태그 없는 글 39건 증가
- 제안: `posts.feed_categories VARCHAR(500) NULL` 추가 (카테고리명을 구분자로 연결, 최대 500자에서 자름). 본문이 아니라 메타데이터라 저작권 원칙(F-004)과 충돌 없음
  - 서버: 수집 시 저장, 재태깅·갱신 시 사용. 기존 글은 다음 갱신 때부터 채워짐 (일괄 백필은 하지 않음)
- 대안: 현행 유지하고 재태깅 손실을 허용함. 카테고리 의존 태그가 4%라 영향은 작음

### 2. `ERROR` 소스의 자동 복귀 (pm)
- 구현: `ERROR` 소스도 늘어난 간격으로 계속 수집하고, 한 번 성공하면 자동으로 `ACTIVE` 복귀
- 기획서(F-002)에는 "관리자가 수동 재개 가능"만 있음. 자동 복귀를 허용할지 확인 요청
  - 서버 의견: 일시적 장애(블로그 점검 등)에 관리자 개입이 필요 없어 자동 복귀 유지가 낫다고 봄

### 3. 로그인 API 일정 앞당기기 (pm·client)
- client 요청: 관리자 화면(A-01~A-04)을 실서버로 확인하려면 `/api/auth/login`, `/api/auth/refresh`, `/api/me`가 필요함
- 현재 계획: 인증 전체는 M4. M1은 개발용 토큰 발급 스크립트(`npm run admin:token`)만 있음
- 제안: F-030 중 **로그인·리프레시·로그아웃·`GET /me`만 M1에 앞당겨 구현**하고, 가입·탈퇴·관심 태그는 M4에 둠
  - 서버 작업량: 반나절 정도. `refresh_tokens` 테이블은 이미 있음 (`0004`)
  - 로그인 5회 실패 잠금까지 같이 구현함 (앞당기는 범위에 포함)
- 대안: M1 동안 client는 개발용 토큰을 헤더에 직접 넣어 확인함

### 4. 로컬 개발 포트 충돌 (사용자 확인 필요)
- `:3000`은 다른 프로젝트(`korail_macro/backend`) node 프로세스가 11-12부터 쓰고 있음. client가 받은 Nest 404는 이 프로세스의 응답이었음
- 지금은 서버를 `PORT=3100`으로 띄워 검증했고, 계속 3100에서 실행 중
- 둘 중 하나가 필요함: (a) 사용자가 해당 프로세스를 종료, (b) `server/.env`의 `PORT`를 3100으로 바꾸고 client Vite proxy 대상도 3100으로 변경
  - `.env`는 내가 수정하지 않으므로 (b)도 사용자 작업임

## 의견

### server (1차)
- 1은 dba 마이그레이션이 필요해서 pm 결정 후 dba에 요청함. 2·3은 pm 결정에 따름. 4는 pm이 사용자에게 전달 부탁

### dba (1차) — 1번
- 데이터 측면에서 추가 찬성. 용량 영향 작음: 평균 50~100바이트 × 10만 건 ≈ 10MB 이하
- 위치는 `posts`가 아닌 `post_search.feed_categories` 권장
  - D-04 원칙: 피드 목록 조회에 안 쓰는 컬럼은 `posts`에 두지 않아 행 크기·버퍼 풀 효율 유지
  - 사용처(수집 저장, 재태깅)가 `post_search` 토큰 재생성과 같은 흐름이라 같은 행에 두는 게 자연스러움
  - FULLTEXT 인덱스 대상에는 넣지 않음 (검색 토큰 반영 여부는 서버 판단, 넣는다면 `body_tokens`에 토큰으로)
- 형태: `VARCHAR(500) NULL`, 구분자는 `\n` 권장. 카테고리명에 쉼표·`|`가 들어가는 피드가 있음. 500자 초과 시 카테고리 단위로 잘라 중간 절단 방지
- 정규화 테이블(`post_feed_categories`)은 불필요: 카테고리로 조회·필터하는 요구가 없고 재태깅 입력으로만 씀
- 백필 미실시 동의. 마이그레이션 `0008`은 pm 결정 후 작성·적용함 (온라인 `ADD COLUMN`, 기본값 NULL이라 즉시 반영 `ALGORITHM=INSTANT` 가능)

### pm (1차)
- M1 검증 결과 확인. 기획 수용 기준(F-002 실패 격리·재시도, F-003 중복 0건, F-004 요약 300자·HTML 제거, F-010 미래 발행일 대체) 충족으로 판단함
- 1·2·3은 아래와 같이 결정. 4는 사용자 확인 사항이라 사용자에게 전달함

### client (1차) — 결정 후 확인
- 3 결정 확인. server 로그인 API 구현 알림 오면 실서버 로그인으로 S-05·A-01~A-04 확인함
- 4: 사용자가 어느 쪽을 골라도 client 코드 변경 없이 대응하도록 Vite proxy 대상을 `VITE_API_TARGET` 환경변수로 받게 함 (기본 `http://localhost:3000`)
  - 3100 유지 시: `VITE_API_MOCK=false VITE_API_TARGET=http://localhost:3100 npm run dev`

### server (2차)
- 1: 위치는 dba 의견대로 `post_search.feed_categories VARCHAR(500) NULL`, 구분자 `\n`, 카테고리 단위로 자르기에 동의함 (pm 결정의 "형태는 dba 판단" 범위로 봄). 검색 토큰(`body_tokens`)에는 넣지 않음. `0008` 적용 확인 후 수집·재태깅에 반영함
- 2·3 결정 수용. 로그인·리프레시·로그아웃·5회 실패 잠금·`GET /me` 구현 착수함

## 결정 (pm)
- 결정 (2026-11-19)
  - 1. 피드 카테고리 보관: **채택, dba안대로 `post_search.feed_categories`** (`VARCHAR(500) NULL`, `\n` 구분, 카테고리 단위 절단, FULLTEXT 대상 아님). 수집·갱신 시 저장, 재태깅에 사용. 일괄 백필 없음
  - 2. `ERROR` 자동 복귀: **채택**. 늘어난 간격으로 계속 수집하고 1회 성공 시 `ACTIVE` 복귀. 수동 재개도 유지
  - 3. 로그인 API 앞당기기: **채택**. F-030 중 로그인·리프레시·로그아웃·로그인 5회 실패 잠금·`GET /me`를 M1로 이동. 가입·탈퇴·관심 태그는 M4 유지. M1 완료 기준에 "관리자 화면을 실서버 로그인으로 확인" 추가
  - 4. 포트 충돌: **사용자 결정 — 기존 프로세스(`korail_macro/backend`) 종료, portfolio 서버는 `:3000` 유지**. `.env`·Vite proxy 변경 없음
- 근거
  - 1: 재태깅이 수집 결과와 달라지는 건 F-005 규칙 불일치임. 메타데이터라 저작권 원칙과 충돌 없고 비용 작음
  - 2: 블로그 점검 같은 일시 장애에 관리자 개입이 필요 없어 1인 운영 부담이 줄어듦. 늘어난 간격 덕분에 실패 소스 부하도 제한됨
  - 3: client가 S-05를 이미 구현했고 서버 작업량이 반나절이라 M1 실서버 검증 가치가 큼. 개발용 토큰 우회는 실제 인증 흐름을 검증하지 못함
