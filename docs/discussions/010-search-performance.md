# 010. 검색 성능: 10만 건 p95 300ms 미달 원인과 개선안

- 상태: decided
- 제기: server
- 관련: dba, pm, client
- 관련 문서: `docs/spec/02-features.md` F-020·F-021, `docs/api/openapi.yaml` `/search`, `docs/schema/decisions.md` D-03·D-04, `server/src/search/`

## 배경
- M3 `GET /api/search` 구현 완료 (질의 생성 `server/src/search/search-query.ts`, 토큰화 `server/src/ingest/tokenizer.ts`)
- `devfeed_perf`(글 10만 건, dba 시드)에 측정 서버(:3100, 스케줄러 끔)를 붙여 API 단위로 측정함
- 정확성(개발 DB 2,383건, 13개 질의): 정밀도 1.00 전부, 재현율은 영문 합성어(`ReplyingKafkaTemplate`, `ReactNative`) 3건 미포함 외 1.00. 영문은 단어 단위 매칭이라 의도한 동작

## 원인 (DB 시간 분해, "개발" 2.4만 건, p50 ms)

| 단계 | 현재 | 대안 |
|---|---|---|
| 전체 건수 COUNT | 140 | 1,001건에서 중단: 19 |
| 관련도 정렬 상위 20건 | `posts` 조인 포함 549 | `post_search`만으로: 134~139 |
| 최신순 상위 20건 | `posts` 조인 274, 50페이지 598 | (같은 원리로 조인 제거 시 130 내외 예상) |
| 매칭 id만 20건 (정렬 없음) | 12 | |

- 가장 큰 비용은 매칭된 2.4만 행마다 `posts`를 PK 조회하는 조인임. 기간·소스 필터와 최신순 정렬에 쓰는 `published_at`·`source_id`가 `posts`에만 있어서 필요함
- 두 번째는 정확한 전체 건수 COUNT
- 단어 구문 매칭(PHRASE)과 모든 bigram 필수(ALL)는 결과가 같았고, 비용 차이는 중간 빈도 단어에서 수 ms 수준이라 병목 아님

## 제안

### A. 전체 건수 상한 1,000 (client·pm)
- 검색은 이미 최대 50페이지(1,000건)만 볼 수 있으므로, COUNT를 1,001건에서 멈추고 응답에 상한 여부를 추가함
  - `total`: 최대 1,000. `totalCapped: boolean` 추가 (true면 화면에 "1,000건 이상")
  - 필드 추가라 호환 변경 (conventions 7절)
- 효과: "개발" 기준 COUNT 140 → 19ms

### B. `post_search`에 `published_at`, `source_id` 비정규화 (dba)
- 검색 정렬·필터를 `post_search` 안에서 끝내고, `posts`는 최종 20건 카드 조회에만 씀
  - D-04에서 검색 데이터를 분리한 원칙과 같은 방향 (피드 쪽 `posts` 행 크기는 그대로)
  - 갱신 시점: 글 저장·발행일 변경 시 (`post_tags.published_at`과 같은 방식), 서버가 같은 트랜잭션에서 씀
  - 태그 필터는 지금처럼 `post_tags` EXISTS (PK 조회)
- 효과(예상): "개발" 관련도·최신순 상위 20건 549/274 → 약 130~140ms
- 대안: `posts`와 조인하되 상위 N건만 먼저 고르는 방식은 필터가 있으면 결과가 달라져 정확성이 깨짐

### A+B 적용 시 예상
- 흔한 단어 c=1: 약 150~170ms (정렬 130 + COUNT 19 + 카드 10). 목표 300ms 충족 예상
- c=10 동시 요청은 로컬 Docker 1대에서 정렬 작업이 겹쳐 여전히 300ms를 넘을 수 있음. 목표의 동시성 기준이 기획서에 없음 → pm 확인 필요

### C. (참고, 이번 측정에는 미반영) 같은 검색어·필터 결과 1분 캐시
- 실서비스에서 인기 검색어 반복 비용을 줄임. 벤치마크가 반복 질의라 캐시를 켜면 수치가 왜곡되므로 측정에서는 끔

## 의견

### server (1차)
- A·B 함께 적용을 제안함. B는 마이그레이션이 필요해서 dba 판단 요청
- pm 확인 요청: p95 300ms 목표의 동시성 기준 (c=1 기준으로 판정해도 되는지)
- 결정 전까지 현재 구현(정확성 확인 완료)은 그대로 두고, 결정 후 명세(A)를 먼저 고친 뒤 구현·재측정함

### client (1차) — A
- A 찬성. 화면에서 볼 수 있는 범위가 이미 50페이지(1,000건)라 정확한 전체 건수는 쓸 데가 없음
- client 반영 계획 (명세 갱신 후)
  - `totalCapped=true`면 건수를 "1,000건 이상"으로 표시
  - 페이지 수 = `ceil(total / size)` (total ≤ 1,000이라 자연히 최대 50). 지금은 `total > 1,000`일 때 마지막 페이지에서 "상위 1,000건까지만 볼 수 있음" 안내를 띄우는데, 조건을 `totalCapped`로 바꿈
  - 필드가 없을 때(구버전 응답)는 `false`로 취급해서 배포 순서와 무관하게 동작
- B는 client 영향 없음. C(1분 캐시)도 client 영향 없음
- 참고: 현재 구현 실서버(:3000) 대조 결과 명세와 일치함 — 응답 `{ items, total, page, size }`, `q` 1자 400 `fieldErrors.q`, `page=51` 400 `fieldErrors.page`, `period`·`sort=LATEST` 동작, 0건 빈 배열

### pm (1차)
- 측정이 구체적이고 원인 분해가 명확함. 정확성(정밀도 1.00)도 확인함. 영문 합성어 미매칭은 허용 (F-020에 명시)
- 동시성 기준 답변: **판정은 c=1 기준**. 1인 운영 포트폴리오 서비스이고 로컬 Docker 1대 환경이라 c=10을 합격 기준으로 두면 인프라 한계를 측정하게 됨. c=10은 참고 지표로 성능 리포트에 함께 남김 (목표 아님, 1초 이내면 양호로 서술)
- A 승인: 검색은 상위 1,000건까지만 볼 수 있어 정확한 전체 건수의 가치가 낮음. 화면은 "1,000건 이상" 표시
- B: 기획 측 이견 없음. 스키마 판단은 dba
- C(1분 캐시): 실서비스 적용 승인, 측정에서는 끔. 단 캐시 대상은 글 ID 목록·건수로 한정하고 회원별 북마크·읽음 플래그는 캐시하지 않음

### dba (1차) — B 대신 `posts` 커버링 인덱스(0009) 권장
- 원인 진단은 동의: 매칭된 수만 행마다 `posts` 클러스터드 행(평균 약 800B)을 PK로 읽는 조인이 병목. 추가로 측정 DB 버퍼 풀이 기본 128MB라 `posts`(81MB) + `post_search`(72MB)가 캐시에 다 안 들어감
- B안을 `devfeed_perf` 복사 테이블로 직접 실험한 결과, **채택하지 않길 권함**
  1. 마이그레이션 비용: FULLTEXT 테이블 컬럼 추가는 `ALGORITHM=COPY`만 가능(D-14). 10만 행에서 **277초**, 그동안 `post_search` 쓰기 잠금 (수집 중단). 이후 컬럼 추가도 매번 같은 비용
  2. 성능: 비정규화 테이블이 기대만큼 빠르지 않았음 (아래 표). FULLTEXT 매칭 결과를 `FTS_DOC_ID`로 행 조회하는 비용이 그대로 남고, 행이 넓어진 만큼 캐시 효율이 떨어짐
- 대안: `posts`에 좁은 커버링 인덱스 추가 — `db/migrations/0009_add_posts_search_filter_index.sql`
  - `idx_posts_search_filter (id, published_at, source_id, source_type)`. 조인이 800B 행 대신 약 30B 인덱스 항목만 읽음 (10만 건 약 3MB, 항상 캐시)
  - 생성 `ALGORITHM=INPLACE, LOCK=NONE`, 10만 행 **56ms**, 쓰기 잠금 없음. 서버 쓰기 경로 변경 없음 (비정규화 동기화 불필요)
  - 주의: 옵티마이저가 기본으로 PRIMARY eq_ref를 고름 (힌트 없으면 215ms). 서버 쿼리에 `JOIN posts p FORCE INDEX (idx_posts_search_filter)` 필수
- 측정 (DB 시간 p95 ms, 20회, `devfeed_perf`, server 측정 서버가 같은 DB에 붙어 있던 상태라 절대값은 흔들림. 상대 비교용)

| 질의 | 현행 (posts 조인) | B안 (post_search 비정규화) | 0009 커버링 인덱스 |
|---|---|---|---|
| redux 관련도 + 1Y + 소스 5개 | 475 (관련도만) | 343 | 86 |
| 인덱스 관련도 + 1Y + 소스 | 214 (관련도만) | 209 | 37 |
| 코드 관련도 + 1Y + 소스 | 198 (관련도만) | 195 | 29 |
| 자바스크립트 관련도 + 1Y + 소스 | 186 (관련도만) | 180 | 35 |
| redux 최신순 | 310 | 306 | 46~224 |
| 코드 최신순 | 179 | 182 | 28~32 |
| 인덱스 최신순 | 184 | 188 | 33~68 |

- 서버 구현 권장 형태 (`db/perf/measure_search.py`의 "권장" 쿼리)
  - 필터·최신순 없음: `post_search`만으로 관련도 상위 20건 → id로 카드 조회 (조인 없음, p95 25~80ms)
  - 기간·소스·유형 필터 또는 최신순: `JOIN posts p FORCE INDEX (idx_posts_search_filter)`
  - 태그 필터: `JOIN post_tags pt ON pt.post_id = s.post_id AND pt.tag_id IN (...)` (p95 23~130ms). 태그 여러 개면 한 글이 중복될 수 있어 `DISTINCT` 또는 EXISTS 유지
  - 관련도 동점 정렬은 `s.post_id DESC`로 대체 가능 (조인 없는 경우)
- A(건수 상한 1,000) 동의: 측정에서도 1,001건 중단 COUNT 2~31ms
- 참고(운영 설정): 버퍼 풀 128MB는 10만 건 규모에 작음. `innodb_buffer_pool_size`는 MariaDB 12에서 기동 시 상한이 정해져 런타임 증설 불가 → `db/conf/devfeed.cnf`에 512MB 설정 + 컨테이너 재시작 필요(사용자 승인 사항). 목표 판정은 현 설정으로도 충족 예상이라 필수는 아님
- 0009는 `devfeed_perf`에만 적용·검증함 (up → down → up). `devfeed`에는 pm 결정 후 적용

### server (2차) — A + 0009 구현·재측정 결과
- 구현 (`server/src/search/search-query.ts`)
  - 기간·소스 필터와 최신순이 없으면 `post_search`만 조회 (관련도 동점은 `s.post_id DESC`)
  - 있으면 `JOIN posts p FORCE INDEX (idx_posts_search_filter)`, 태그 필터는 `post_tags` EXISTS (`s.post_id` 기준, 조인 불필요)
  - 건수: `SELECT COUNT(*) FROM (... LIMIT 1001)`, 응답 `total ≤ 1000` + `totalCapped` (명세 반영)
  - C: 같은 검색어·필터의 글 ID·건수 1분 캐시(최대 500개, 오래 안 쓴 순 제거). 회원 플래그는 매번 조회. `SEARCH_CACHE_ENABLED=false`로 끔
- 측정: `devfeed_perf` 글 10만 건, 캐시 끔, 질의당 40회, API 응답 시간(ms)

## 결정 (pm)
- 결정 (2026-11-19, dba 의견 전 pm 범위)
  - 판정 기준: 글 10만 건, c=1, API p95 300ms. c=10은 참고 지표로 기록
  - A 채택: `total` 최대 1,000 + `totalCapped` 추가 (호환 변경)
  - C 채택: 검색어·필터 기준 1분 캐시, 회원 플래그 제외, 측정 시 끔
  - B: dba 의견 후 확정
- 결정 보충 (2026-11-19, dba 1차 반영)
  - B 기각: FULLTEXT 테이블 컬럼 추가가 `ALGORITHM=COPY`라 10만 행 277초 쓰기 잠금(수집 중단), 성능 이득도 거의 없음(실측)
  - 대안 채택: `0009` `posts` 커버링 인덱스 `idx_posts_search_filter (id, published_at, source_id, source_type)`. 온라인 생성 56ms, 쓰기 경로 변경 없음
  - 서버 쿼리 형태는 dba 권장안 기준: 필터·최신순 없으면 `post_search`만, 있으면 `FORCE INDEX (idx_posts_search_filter)` 조인. 최종 형태는 server가 재측정으로 확정
  - 버퍼 풀 512MB 증설: 이번에는 하지 않음. 현 설정으로 목표 충족 예상. M6 출시 환경 정리 때 다시 검토 (컨테이너 재시작은 사용자 승인 사항)
- 근거: 1인 서비스의 실제 부하 수준과 측정 환경 한계를 반영, 50페이지 상한으로 정확한 총계의 효용 낮음
