# 044. 검색엔진 노출 개선 (SEO)

- 상태: decided
- 제기: pm
- 관련: server, client (nginx는 pm)
- 관련 문서: docs/spec/02-features.md F-095, docs/spec/04-roadmap.md M14

## 배경
- 사용자가 Google Search Console·네이버 서치어드바이저 등록과 소유 확인 완료 (043)
- 실서버 점검 결과 (2026-11-23)
  - 모든 경로가 같은 `index.html`을 줌. `<div id="root"></div>`만 있고 본문 없음 (CSR)
  - 제목·설명·OG가 전 페이지 동일. `RouteTitle`은 JS 실행 후 `document.title`만 바꿈. canonical 없음
  - `client/public/sitemap.xml`은 정적 목록 10개. 게시글 상세 URL 0개
  - RSS 없음. `/rss.xml` 등이 SPA 폴백으로 200 + 메인 화면
  - 없는 경로도 200 (soft 404)
  - `/`는 클라이언트에서 `/tech`로 넘김
- 네이버 Yeti는 JS 렌더링이 약해 지금 구조로는 본문 색인이 거의 안 됨. Google도 렌더 대기열 때문에 늦음
- 우리 사이트 고유 페이지는 자유 게시판 글 상세(`/community/posts/:id`)뿐. 기술·보안 뉴스 카드는 외부 원문 링크라 색인 가치 낮음 → **자유 게시판 우선**

## 제안 / 한계점

### 목표
- 자유 게시판 글 상세가 JS 없이도 제목·본문·작성일이 HTML에 들어간 상태로 응답
- 게시글 URL이 sitemap·RSS로 자동 노출
- 측정: 4주 뒤 Search Console·서치어드바이저에서 색인된 게시글 수, 검색 노출 수

### 범위 (MVP)
| ID | 항목 | 내용 | 담당 안 |
|---|---|---|---|
| S1 | 동적 sitemap | `/sitemap.xml` = 고정 목록 화면 + 공개 상태 자유 게시판 글 전부(`lastmod` = 수정 시각). 숨김·삭제 글 제외. 5만 건 넘으면 sitemap index로 분할 | server |
| S2 | 자유 게시판 RSS | `/community/rss.xml` 최근 공개 글 50건(제목·요약·링크·작성일). `<head>`에 `alternate` 링크. 네이버 RSS 제출용 | server |
| S3 | 페이지별 HTML 머리말 | 경로별 `<title>`·description·canonical·OG·twitter. 글 상세는 글 제목, 본문 앞 120자, 작성자, 작성일 | server(HTML 응답) + client(라우트 이동 시 갱신) |
| S4 | 글 상세 본문 HTML | `/community/posts/:id` 응답에 본문(무해화된 HTML)·댓글 일부를 `#root` 안에 넣어 보냄. React는 마운트 시 교체해도 됨 (hydrate 필수 아님) | server + client |
| S5 | 구조화 데이터 | 글 상세에 JSON-LD. 질문(채택 있음)은 `QAPage`, 그 외 `DiscussionForumPosting` | server |
| S6 | 실제 404 | 없는 글 id, 숨김·삭제 글 → 404 상태 코드 + 안내 화면. 알 수 없는 경로도 404 | server + client + pm(nginx) |
| S7 | 목록 화면 머리말 | `/community`·`/tech`·`/security`와 정렬 화면도 S3 방식으로 고유 제목·설명. 목록 본문 HTML은 자유 게시판 최신 20건만 | server |

### Next (이번 범위 밖)
- 기술·보안 뉴스 상세 페이지 신설 (원문 요약 중복 문제로 보류)
- 전체 SSR 프레임워크 전환
- 정렬 화면(`/popular` 등)은 canonical을 기본 목록으로 돌릴지 여부는 S3 결정 후 재검토

### 원칙
- **봇·사람 같은 HTML**: User-Agent로 응답을 바꾸지 않음 (클로킹 금지). 모든 방문자에게 같은 HTML을 줌
- 무해화는 032 XSS 기준 그대로 사용. JSON-LD 안 문자열도 `</script>` 이스케이프
- 성능: 글 상세 HTML 응답 p95 300ms 이하, 짧은 캐시 허용(글 수정·숨김 반영 지연 최대 5분)
- 로그인·개인 화면(`/me/`, `/admin`, `/onboarding/`, `/community/new`, 수정 화면)은 `noindex` 유지
- `/` 는 서버에서 `/tech` 로 301 하거나, `/` 자체를 canonical 목록으로 둘지 server·client 의견 받음

### 구조 제안 (pm 안, 확정 아님)
```
브라우저/봇 ─ nginx
  ├ /assets/, 정적 파일 ─ dist-root (기존)
  ├ /sitemap.xml, /community/rss.xml ─ server
  ├ /community/posts/:id, 목록 화면 ─ server (index.html 템플릿에 머리말·본문 주입)
  └ 그 외 ─ index.html (기존 SPA)
```
- server가 빌드된 `dist-root/index.html`을 템플릿으로 읽어 주입하는 방식을 제안. client 빌드 산출물 경로·자산 해시가 바뀌어도 동작해야 함
- nginx 라우팅 변경은 pm이 server 구현 확인 후 적용

### 요청
- server: S1~S7 가능 여부, 템플릿 주입 방식 vs 대안, API·캐시 설계, 예상 기간
- client: S3 라우트 이동 시 머리말 갱신 방식, S4 서버 HTML과 React 마운트 충돌 여부, S6 404 화면, 정적 `sitemap.xml` 제거 시점

## 의견

### server (1차) — 가능 여부·설계
- **S1~S7 모두 가능**. 스키마 변경 없음 (`community_posts.status`·`published_at`·`edited_at`, 기존 인덱스로 충분). 예상 약 3일
  - 1단계 S1·S2 (0.5일): nginx에 경로 2개만 추가하면 되고 지금 SPA와 충돌 없음 → 먼저 배포해서 Search Console·서치어드바이저에 바로 제출
  - 2단계 S3·S4·S5·S7 (1.5일), 3단계 S6 (0.5일 + nginx)
- **템플릿 주입 방식 찬성** (pm 안 그대로). 대안(SSR 프레임워크, 프리렌더 서비스)보다 바뀌는 곳이 적고 클로킹 걱정 없음
  - server가 `client/dist-root/index.html`을 읽음 (경로는 env `WEB_INDEX_PATH`). 파일 수정 시각이 바뀌면 다시 읽으므로 client가 `build:web`만 배포해도 server 재시작 필요 없음. 자산 해시는 index.html 안 그대로 쓰므로 영향 없음
  - **client 요청**: index.html에 주입 표시 2개 `<!--app-head-->`(`<head>` 안, 기본 title·description·OG 대신)와 `<!--app-body-->`(`<div id="root"><!--app-body--></div>`)를 넣어 주기 바람. 표시가 없으면 server는 주입 없이 원본 그대로 줌 (빌드가 바뀌어도 화면은 안 깨짐)
  - Nest 전역 접두사 `/api`에서 웹 경로만 제외 (`setGlobalPrefix('api', { exclude })`). 새 모듈 `server/src/web/`
- **S1 sitemap** `GET /sitemap.xml`: 고정 목록 화면 + `VISIBLE` 글 전부(`lastmod` = `edited_at ?? published_at`). 5만 건 넘으면 `/sitemap-community-N.xml` index로 자동 분할. 10분 캐시
- **S2 RSS** `GET /community/rss.xml`: RSS 2.0, 최근 `VISIBLE` 50건 (제목·`posts.summary`·링크·`pubDate`·작성자 닉네임). 10분 캐시. `<head>` alternate는 S3 주입에 포함 (1단계에선 client index.html에 고정으로 넣어도 됨)
- **S3·S7 머리말**: 경로 표(정규식 → 제목·설명·canonical·robots)를 server에 둠. 글 상세는 글 제목 / 본문 앞 120자 / `article:author`·`published_time` / OG 이미지는 기존 `og.png`
  - 정렬 화면(`/tech/comments` 등)은 canonical을 기본 목록으로 두길 제안 (같은 글 모음이라 중복 신호 방지). pm 결정 바람
  - 개인 화면(`/me/`, `/admin`, `/onboarding/`, `/community/new`, 수정)은 `noindex, nofollow` 주입
  - 모든 값은 HTML 속성 이스케이프. 사용자 입력(제목·닉네임)이 머리말에 들어가므로 e2e에 XSS 케이스 추가
- **S4 본문 HTML**: 서버는 지금 마크다운을 렌더링하지 않음 → `marked` + `sanitize-html` 추가해 032 허용 목록(태그·속성·`http(s)`/`mailto` 링크, `rel="nofollow ugc noopener"`)으로 변환. client `react-markdown` 출력과 글자 단위로 같지는 않지만 React가 마운트 때 `#root`를 통째로 바꾸므로 문제없음 (hydrate 아님)
  - 넣는 것: 제목, 말머리, 작성자 닉네임, 작성일, 본문, 채택 댓글 + 최상위 댓글 최신 20개(삭제 제외, 본문은 같은 무해화). 대댓글은 넣지 않음
  - S7 목록 본문: 자유 게시판 최신 20건 제목·요약·링크만
- **S5 JSON-LD**: 질문 + 채택 있음 → `QAPage`(`acceptedAnswer`, 나머지 댓글 `suggestedAnswer`, `answerCount`), 그 외 `DiscussionForumPosting`(`commentCount`·`interactionStatistic` 좋아요). `JSON.stringify` 뒤 `<`·`>`·`&`·U+2028/2029를 `\uXXXX`로 바꿔 `</script>` 탈출 막음
- **S6 404**: 없는 id·`HIDDEN`·`DELETED` → 404 + 템플릿(`noindex`, 본문 비움 → client가 404 화면). 알 수 없는 경로는 **nginx가 정적 파일이 아닌 HTML 요청을 전부 server로** 보내고 server가 경로 표에 없으면 404
  - 한계: client 라우트가 늘면 server 경로 표도 같이 늘려야 함 (안 하면 새 화면이 404). client가 새 라우트를 만들면 discussion에 적기로 규칙화 제안. e2e로 client 라우트 목록 파일과 대조하는 검사도 둘 수 있음 (client가 경로 목록을 파일로 내보내 주면)
  - 한계: HTML이 server를 거치므로 **server가 죽으면 화면도 안 뜸**. nginx `error_page 502 503 504 = @spa`로 원본 index.html 폴백 제안 (pm nginx)
- **`/`**: server에서 `/tech`로 **301** 제안. client가 이미 `/tech`로 넘기고 있어 사용자 화면 차이 없고, canonical이 하나로 정리됨
- **캐시·성능**: 단일 프로세스라 메모리 캐시. 글 상세 HTML 5분(최대 500개), sitemap·RSS·목록 10분. server를 거친 글 수정·숨김·삭제는 그 글 캐시를 바로 지우므로 실제 지연은 다른 경로(정합성 스크립트 등)만 최대 5분. 응답에 `Cache-Control: public, max-age=60`. 쿼리 2~3개(글+작성자, 댓글, 태그) + 렌더라 p95 수십 ms 예상, 측정해서 남김
- 정적 `client/public/sitemap.xml`은 server S1 배포 + nginx 전환 뒤 client가 제거

### client (1차)
- 결론: S1~S7 모두 가능. pm 구조안(server가 `dist-root/index.html`을 템플릿으로 주입) 찬성. hydrate 없이 지금 `createRoot` 그대로 감. client 작업 약 1일

#### 템플릿 계약 (client가 `index.html`에 넣을 것)
- `<head>` 안 경로별로 바뀌는 태그를 `<!--seo:head-->` … `<!--/seo:head-->` 구간으로 묶음
  - 대상: title, description, canonical, og:title·description·url·type, twitter:title·description, robots
  - 각 태그에 `data-seo` 속성을 붙임
  - 기본값은 지금 사이트 공통 값이라 server가 주입하지 않아도 지금과 같음
- `<div id="root"><!--seo:body--></div>`: server는 이 표시를 본문 HTML로 바꿈
- 그 밖에 JSON-LD·RSS `alternate`도 server가 head 구간에 `data-seo`를 붙여 넣으면 client가 같이 관리함
- Vite 빌드가 HTML 주석을 남기는지 확인함. `check-build --release`에 두 표시가 결과에 있는지 검사를 추가함
- 자산 해시는 템플릿 안 `<script>`·`<link>`에 이미 들어 있어 server는 건드릴 필요 없음
- `build:web`은 출력 폴더를 비우고 다시 쓰므로 잠깐 `index.html`이 없는 순간이 있음
  - server는 마지막으로 정상 읽은 템플릿을 메모리에 두고, 파일 mtime이 바뀌면 다시 읽기를 요청함

#### S3 라우트 이동 시 머리말 갱신
- `RouteTitle`을 `useSeoHead`로 넓힘
  - 경로마다 title·description·canonical·og·twitter·robots를 `data-seo` 태그에 바로 씀 (라이브러리 추가 없음)
  - 첫 로드 값이 server 주입값과 같아 깜빡임 없음
- 글 상세는 데이터를 받은 뒤 글 제목과 본문 앞 120자를 씀
  - 120자는 마크다운 기호를 뺀 평문 기준임
  - 같은 규칙을 server와 맞추되 몇 글자 차이는 문제 삼지 않음
- canonical은 `https://formulous.org` + 경로, 쿼리는 뺌 (필터·검색어 쿼리는 같은 목록으로 봄)
  - 정렬 화면은 경로가 달라 각자 canonical. pm 보류 항목은 그대로 둠
- 다른 화면으로 옮기면 앞 화면의 JSON-LD·`alternate` 같은 `data-seo` 추가 태그는 지움
- `/search`는 `noindex` 추가를 제안함 (검색 결과는 색인 가치가 낮고 중복이 많음)
- 지금 `noindex` 목록(글쓰기·수정·로그인·가입·온보딩·내 정보·관리자)은 유지함

#### S4 server 본문 HTML과 React 마운트
- 충돌 없음. `createRoot().render`가 첫 커밋 때 `#root` 안 내용을 비우고 그림 (hydrate가 아니라 불일치 경고도 없음)
- 글 상세 화면은 따로 받는 코드(lazy)라, 그대로 두면 아래 순서로 바뀌어 화면이 덜컹거림
  1. server 본문이 보임
  2. 로딩 스피너로 바뀜
  3. 실제 화면으로 바뀜
- client 대응 두 가지
  1. `main.tsx`에서 현재 경로가 `/community/posts/:id`면 그 화면 코드를 먼저 불러온 뒤 render함. 스피너 단계가 없어짐
  2. 선택 사항: server가 `<script type="application/json" id="seo-data">`에 상세 API와 같은 모양의 글 JSON을 넣어 주면, client가 TanStack Query 첫 값으로 씀
     - 글을 다시 받지 않고 바로 같은 내용이 보임
     - 실행되지 않는 JSON이라 CSP·XSS 부담이 적음. `<` 이스케이프는 필요함
     - 없어도 동작하므로 server 일정에 따라 2단계로 둬도 됨
- server 본문 마크업은 지금 화면 클래스와 맞출 필요 없음. 의미 태그만 있으면 됨: `<article><h1>`, 작성자, `<time datetime>`, 본문, 댓글 `<ol>`
  - 스타일 없이도 읽히는 정도면 충분하고, React가 곧 교체함
- **주의**: 본문은 client에서 마크다운(`react-markdown`)으로 그림
  - server도 마크다운을 HTML로 바꾼 뒤 032 기준으로 무해화해야 함
  - 원문 마크다운을 그대로 넣으면 봇이 `**` 같은 기호를 본문으로 읽음
- 목록(S7) 최신 20건 본문도 같은 방식임 (제목 링크 `<a href="/community/posts/:id">` 목록이면 충분)

#### S6 404
- client: 알 수 없는 경로(`NotFoundPage`)와 글 없음 화면(`글을 찾을 수 없어요`)에 `noindex`와 "페이지를 찾을 수 없어요" 제목을 씀
  - 상태 코드는 client가 못 바꾸니 server·nginx 몫임
- 알 수 없는 경로 판정용으로 client가 빌드 때 `dist-root/routes.json`을 만들어 줄 수 있음
  - 공개 경로 패턴 목록 (예: `/tech`, `/community/posts/:id`)
  - server·nginx가 같은 목록을 따로 들고 있지 않아도 됨
  - 필요하면 server가 말해 주면 넣음
- 404 응답 본문도 같은 템플릿(`index.html`)이면 React가 404 화면을 그림. 글 없음은 server가 404 + 템플릿으로 주면 됨

#### `/`
- server(또는 nginx) 301 `/` → `/tech` 찬성
  - 이미 client가 `/tech`로 넘기고 있고, `/`를 따로 두면 `/tech`와 중복 색인됨
  - client 쪽 넘김은 안전망으로 남김

#### 정적 `sitemap.xml` 제거 시점
- nginx가 `/sitemap.xml`을 server로 넘기도록 바뀌고 pm이 실서버 응답을 확인한 다음 client 배포에서 지움
  - 그 전에 지우면 그 사이 404가 남
  - 같이 `check-build` 대상에서도 뺌
- `robots.txt`의 `Sitemap:` 주소는 그대로라 바꿀 것 없음

#### client 작업 순서
1. `index.html` 표시·`data-seo`
2. `useSeoHead`
3. 글 상세 먼저 불러오기
4. 404·검색 `noindex`
5. `check-build` 검사
6. (server가 넣어 주면) `seo-data` 첫 값 사용
7. 정적 sitemap 제거

- 1~5는 server 구현 전에도 배포 가능함. 템플릿 표시만 생기고 동작은 지금과 같음

### pm (1차 결정, server 의견 기준) — 2026-11-23
- **정렬 화면 canonical → 기본 목록** 채택. `/tech/popular`·`/tech/comments`·`/security/popular`·`/community/popular`·`/community/comments`·`/community/likes`는 canonical을 각 기본 목록(`/tech`·`/security`·`/community`)으로 두고 **sitemap에서 뺌**. robots는 `index, follow` 유지 (링크 따라 글 수집되게)
- **`/` → `/tech` 301** 채택. 첫 화면을 바꾸는 건 이번 범위 밖
- 단계 진행 승인: 1단계 S1·S2 바로 착수·배포. 2단계 이후는 client 의견 받은 뒤 진행
- 경로 표 동기화: 제안대로 규칙화. client 라우트가 바뀌면 discussion에 적고, client가 내보내는 경로 목록 파일과 server 경로 표를 e2e로 대조함. 파일 형식·위치는 client 의견 받음
- server 장애 시 원본 index.html 폴백(`error_page 502 503 504 = @spa`)은 pm이 nginx 전환 때 같이 넣음
- nginx 1단계: S1·S2 배포 알림 받으면 `= /sitemap.xml`, `= /community/rss.xml`을 server로 보내는 설정을 pm이 넣음

### client (2차) — server 1차와 맞춤
- server 1차와 client 1차를 같은 시각에 써서 서로 보지 못했음. 다른 점만 정리함
- **주입 표시 이름은 server 안(`app-head`·`app-body`)을 따름**. 다만 head는 여는 표시와 닫는 표시 한 쌍으로 하길 요청함
  - `<!--app-head-->` 기본 title·description·canonical·OG·twitter `<!--/app-head-->` 형태이고, server는 이 구간을 통째로 바꿈
  - 이유: nginx 502 폴백(`@spa`)·개발 서버·주입 실패 때 원본 index.html이 그대로 나가도 기본 머리말이 남아야 함. 표시 하나만 두고 기본값을 빼면 그때 제목이 없어짐
  - 구간 안 태그에는 `data-seo`를 붙여 client가 라우트 이동 때 갱신함. server가 주입하는 태그에도 `data-seo`를 붙여 주길 바람
    - 대상: JSON-LD·`alternate` 포함
    - 이유: 화면을 옮길 때 client가 앞 화면 태그를 지울 수 있게 하려는 것임
  - body는 server 안 그대로 `<div id="root"><!--app-body--></div>`
- **라우트 공유: client가 `dist-root/routes.json`을 빌드 때 만들어 주는 것으로 확정 제안**
  - 내용: 공개 경로 패턴 목록 + 경로별 `noindex` 여부
  - 원본은 client 라우트 표 하나이고, 빌드 검사로 `App.tsx` 라우트와 어긋나지 않게 묶음
  - 제안: server가 이 파일을 index.html처럼 수정 시각 기준으로 다시 읽어 **404 판정에 바로 씀**
    - 그러면 client가 라우트를 추가해도 server 배포 없이 404가 나지 않음. discussion에 적는 규칙은 머리말(제목·설명)이 필요한 공개 화면만 남기면 됨
    - server 머리말 표에 없는 경로는 기본 머리말로 둠
  - 이 방식이 어려우면 server 안(e2e 대조)도 괜찮음
- **정렬 화면 canonical을 기본 목록으로 두는 server 안에 동의함**. pm이 정하면 `useSeoHead`도 같은 규칙으로 맞춤
- 개인 화면 robots는 server 안대로 `noindex, nofollow`로 맞춤. `/search`도 같은 값을 주길 제안함 (client 1차)
- 1단계(S1·S2) 배포 때 RSS `alternate`는 client가 index.html head 구간에 고정으로 넣음
- `seo-data` JSON(client 1차 S4 선택 사항)은 server 2단계 이후로 미뤄도 됨. client는 없어도 글 상세를 먼저 불러와 스피너 단계를 없앰

### server (2차) — client 제안 수용, 1단계 착수
- 주입 표시 계약 수용: `<!--seo:head-->` … `<!--/seo:head-->` 구간을 server가 통째로 경로별 태그(`data-seo` 포함)로 바꿈, `<!--seo:body-->`는 본문 HTML로 바꿈. 표시가 없거나 짝이 안 맞으면 원본 그대로 줌
- 템플릿 읽기: 마지막으로 정상 읽은 템플릿을 메모리에 두고 mtime이 바뀌면 다시 읽음. 읽기 실패(빌드 중 파일 없음)면 이전 템플릿 계속 씀 → 요청대로
- 마크다운 → HTML → 032 기준 무해화 server가 함 (2단계)
- `seo-data` JSON: 받음. 2단계에서 상세 API(`GET /api/community/posts/:id` 비로그인 응답)와 같은 모양으로 넣음. `<`·`>`·`&`·U+2028/2029 이스케이프. 로그인 사용자 값(`likedByMe` 등)은 비로그인 기준이라 client가 로그인 상태면 다시 받아야 함
- `routes.json`: 받음. `dist-root/routes.json` 공개 경로 패턴 목록(`:param` 표기)을 server가 템플릿과 같이 읽어 404 판정에 씀 → server 경로 표는 머리말(제목·설명·canonical·robots)만 들고, e2e에서 두 목록 대조
- `/search` `noindex` 동의 (server 주입도 같게 함)
- canonical: pm 결정대로 정렬 화면은 기본 목록으로 → client `useSeoHead`도 같은 규칙으로 맞춰 주기 바람 (client 1차의 "정렬 화면은 각자 canonical"과 다름)
- 1단계 S1·S2 명세는 `docs/api/web.md`에 둠 (JSON API가 아니라 `/api` 밖 경로라 openapi와 분리)

## 결정 (pm)

- 결정
  1. **방식**: server가 `dist-root/index.html`을 틀로 써서 머리말과 본문을 채워 넣음. hydrate는 쓰지 않음
  2. **틀 표시 형식**: client 안을 채택함
     - `<!--seo:head-->` … `<!--/seo:head-->` 구간 + `data-seo` 태그, `<div id="root"><!--seo:body--></div>`
     - server는 구간 전체를 교체함. 표시가 없으면 원본 그대로 응답함
     - 마지막으로 정상 읽은 틀을 메모리에 두고, mtime이 바뀌면 다시 읽음
  3. **경로 정보는 한 곳에만 둠**: client가 빌드 때 `dist-root/routes.json`을 만듦
     - 항목: 패턴, 제목, 설명, robots, canonical 대상
     - server는 이 파일로 머리말을 만들고, 목록에 없는 경로는 404로 판정함
     - server 쪽 별도 경로 표는 두지 않음. 라우트 추가가 client 한 곳에서 끝나서 동기화 누락이 생기지 않음
  4. **정렬 화면**: canonical은 기본 목록으로 둠. client 의견의 "각자 canonical"은 채택하지 않음

  5. **`/search`**: `noindex, follow`. 그 밖의 쿼리는 canonical에서 뺌

     - 개인 화면은 `noindex, nofollow`
