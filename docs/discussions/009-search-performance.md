# 009. 검색 성능: 10만 건 p95 300ms 미달 원인과 개선안

- 상태: open
- 제기: server
- 관련: dba, pm, client
- 관련 문서: `docs/spec/02-features.md` F-020·F-021, `docs/api/openapi.yaml` `/search`, `docs/schema/decisions.md` D-03·D-04, `server/src/search/`

## 배경
- M3 `GET /api/search` 구현 완료 (질의 생성 `server/src/search/search-query.ts`, 토큰화 `server/src/ingest/tokenizer.ts`)
- `devfeed_perf`(글 10만 건, dba 시드)에 측정 서버(:3100, 스케줄러 끔)를 붙여 API 단위로 측정함
- 정확성(개발 DB 2,383건, 13개 질의): 정밀도 1.00 전부, 재현율은 영문 합성어(`ReplyingKafkaTemplate`, `ReactNative`) 3건 미포함 외 1.00. 영문은 단어 단위 매칭이라 의도한 동작

## 원인 (DB 시간 분해, "개발" 2.4만 건, p50 ms)

| 단계 | 현재 | 대안 |
|---|---|---|
| 전체 건수 COUNT | 140 | 1,001건에서 중단: 19 |
| 관련도 정렬 상위 20건 | `posts` 조인 포함 549 | `post_search`만으로: 134~139 |
| 최신순 상위 20건 | `posts` 조인 274, 50페이지 598 | (같은 원리로 조인 제거 시 130 내외 예상) |
| 매칭 id만 20건 (정렬 없음) | 12 | |

- 가장 큰 비용은 매칭된 2.4만 행마다 `posts`를 PK 조회하는 조인임. 기간·소스 필터와 최신순 정렬에 쓰는 `published_at`·`source_id`가 `posts`에만 있어서 필요함
- 두 번째는 정확한 전체 건수 COUNT
- 단어 구문 매칭(PHRASE)과 모든 bigram 필수(ALL)는 결과가 같았고, 비용 차이는 중간 빈도 단어에서 수 ms 수준이라 병목 아님

## 제안

### A. 전체 건수 상한 1,000 (client·pm)
- 검색은 이미 최대 50페이지(1,000건)만 볼 수 있으므로, COUNT를 1,001건에서 멈추고 응답에 상한 여부를 추가함
  - `total`: 최대 1,000. `totalCapped: boolean` 추가 (true면 화면에 "1,000건 이상")
  - 필드 추가라 호환 변경 (conventions 7절)
- 효과: "개발" 기준 COUNT 140 → 19ms

### B. `post_search`에 `published_at`, `source_id` 비정규화 (dba)
- 검색 정렬·필터를 `post_search` 안에서 끝내고, `posts`는 최종 20건 카드 조회에만 씀
  - D-04에서 검색 데이터를 분리한 원칙과 같은 방향 (피드 쪽 `posts` 행 크기는 그대로)
  - 갱신 시점: 글 저장·발행일 변경 시 (`post_tags.published_at`과 같은 방식), 서버가 같은 트랜잭션에서 씀
  - 태그 필터는 지금처럼 `post_tags` EXISTS (PK 조회)
- 효과(예상): "개발" 관련도·최신순 상위 20건 549/274 → 약 130~140ms
- 대안: `posts`와 조인하되 상위 N건만 먼저 고르는 방식은 필터가 있으면 결과가 달라져 정확성이 깨짐

### A+B 적용 시 예상
- 흔한 단어 c=1: 약 150~170ms (정렬 130 + COUNT 19 + 카드 10). 목표 300ms 충족 예상
- c=10 동시 요청은 로컬 Docker 1대에서 정렬 작업이 겹쳐 여전히 300ms를 넘을 수 있음. 목표의 동시성 기준이 기획서에 없음 → pm 확인 필요

### C. (참고, 이번 측정에는 미반영) 같은 검색어·필터 결과 1분 캐시
- 실서비스에서 인기 검색어 반복 비용을 줄임. 벤치마크가 반복 질의라 캐시를 켜면 수치가 왜곡되므로 측정에서는 끔

## 의견

### server (1차)
- A·B 함께 적용을 제안함. B는 마이그레이션이 필요해서 dba 판단 요청
- pm 확인 요청: p95 300ms 목표의 동시성 기준 (c=1 기준으로 판정해도 되는지)
- 결정 전까지 현재 구현(정확성 확인 완료)은 그대로 두고, 결정 후 명세(A)를 먼저 고친 뒤 구현·재측정함
