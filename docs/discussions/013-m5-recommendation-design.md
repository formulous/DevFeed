# 013. M5 추천(F-042) 설계: 점수·다양성·스냅샷·노출/클릭 기록

- 상태: open
- 제기: server
- 관련: pm, dba, client
- 관련 문서: `docs/spec/02-features.md` F-042, `docs/api/openapi.yaml` `/recommendations`·`/posts/{postId}/views`, `docs/schema/decisions.md` D-10·D-10a, `docs/discussions/002`(10번), `004`(9번)

## 배경
- 002에서 추천 로그는 골격만 합의하고 세부는 M5로 미룸. 004에서 API 형태(응답마다 `recommendationId`, 스냅샷 10분, 응답 시점 노출 기록)는 확정
- 아래는 서버 구현안. 수치(가중치 등)는 기획 판단이 필요해서 pm 확인을 요청함. 명세(`openapi.yaml`) 변경은 없음

## 제안

### 1. 사용자 태그 선호도
| 근거 | 가중치 | 시간 감쇠 |
|---|---|---|
| 관심 태그 (`user_interest_tags`) | 태그당 3.0 | 없음 |
| 최근 30일 북마크한 글의 태그 | 글마다 2.0 × 감쇠 | `0.5^(경과일/7)` (반감기 7일) |
| 최근 30일 읽은 글의 태그 | 글마다 1.0 × 감쇠 | 같음 |
- 태그별로 합산한 뒤 최댓값으로 나눠 0~1로 정규화
- 근거별 기여도를 같이 보관해 "추천 이유"에 사용

### 2. 후보와 점수
- 후보: 최근 14일 발행 글 중 내가 읽지 않은 글, 그리고 선호 태그가 하나 이상 붙은 글
  - 조회: `post_tags`의 `(tag_id, published_at, post_id)` 인덱스로 선호 상위 태그(최대 30개)별 최근 14일 글을 모음
- 점수 = 0.7 × 태그 일치 + 0.2 × 인기도 + 0.1 × 최신성
  - 태그 일치: 글 태그들의 선호도 합 (상위 태그 rank 가중 없이 합산, 최대 1로 자름)
  - 인기도: `log(1 + 조회수) / log(1 + 후보 중 최대 조회수)`
  - 최신성: `1 - 경과시간 / 14일`
- 상위 200건까지만 순위를 만듦 (무한 스크롤 10페이지)

### 3. 다양성 보정
- 점수 순으로 하나씩 배치하되, 직전 2개가 같은 소스면 그 소스가 아닌 다음 후보를 먼저 배치함 (같은 소스 최대 연속 2개)
- 남은 후보가 모두 같은 소스뿐이면 그대로 이어 붙임 (빈 화면보다 낫다고 봄)

### 4. 추천 이유 (`reasons`, 004 형태)
- 점수에 가장 크게 기여한 태그 1~2개를 근거별로 표시
  - 관심 태그면 `INTEREST_TAG`, 북마크 근거면 `BOOKMARK`, 읽은 기록 근거면 `READ_HISTORY` + `tagName`
- 콜드 스타트 결과는 `POPULAR` 하나

### 5. 콜드 스타트 (`fallback: true`)
- 선호 태그가 하나도 없으면(관심 태그 없음 + 최근 30일 읽기·북마크 없음) 최근 14일 글을 조회수 내림차순(동점 최신순), 읽은 글 제외로 채움
- 008(인기 글 조회수 1 이상)과 달리 조회수 0인 글도 포함함. 추천 화면이 비면 안 되기 때문 → pm 확인 요청

### 6. 스냅샷과 페이지네이션 (004 9번)
- 첫 요청에서 순위 목록(최대 200건)을 계산해 서버 메모리에 10분 보관, 커서 = `{스냅샷 ID, 다음 위치}`
- 스냅샷이 없거나 만료·다른 회원 것이면 400 `INVALID_CURSOR` → client는 첫 페이지부터 다시 요청 (004 합의)
- 한계: 서버 인스턴스가 여러 대면 스냅샷이 공유되지 않음. 1인 서비스 단일 인스턴스 전제

### 7. 노출·클릭 기록 (D-10, D-10a)
- 노출: 응답마다 `recommendationId`(UUID v4)를 새로 만들고 카드마다 1행 INSERT
  - `request_id`, `user_id`, `post_id`, `algorithm`, `position`(스냅샷 안 전체 순위, 1부터), `reason`(첫 번째 이유를 `INTEREST_TAG:Kafka` 형태 문자열, 200자 이내), `shown_at`
  - `algorithm`: 일반 `TAG_V1`, 콜드 스타트 `COLD_POPULAR` (클릭률을 분리해서 보기 위함)
  - 한 페이지 20행을 한 번에 INSERT. 기록이 실패해도 추천 응답은 내려줌 (로그만 남김)
- 클릭: 기존 `POST /posts/{postId}/views` 본문의 `recommendationId`로 처리
  - `UPDATE recommendation_impressions SET clicked_at = COALESCE(clicked_at, now) WHERE request_id = ? AND post_id = ? AND user_id = ?`
  - 다른 회원의 `recommendationId`나 비회원 요청은 무시 (조회수 기록은 그대로)
  - 같은 카드를 여러 번 눌러도 첫 클릭 시각만 남김
- 클릭률 = `COUNT(clicked_at) / COUNT(*)`, 알고리즘·일자별

### 8. 배치 (D-10a 순서)
- 매일 04:00 KST: ① 최근 7일 일별 집계 upsert(`recommendation_daily_stats`) → ② 성공했을 때만 90일 지난 노출 원본 1,000건씩 삭제
- M4에서 만든 일일 정리 작업에 이어서 실행

### 9. 성능 목표·검증
- 목표: 추천 API c=1 p95 300ms (`devfeed_perf`: 회원 1만, 읽은 기록 191만, 북마크 50만 기준)
  - 선호도 계산: 회원 1명의 최근 30일 읽기·북마크(평균 수십~수백 건)와 그 태그
  - 후보 수집: 선호 상위 30개 태그 × 최근 14일 글 → 최대 수천 건
- 검증: 단위 테스트(점수·감쇠·다양성·이유·커서), e2e(콜드 스타트 → 관심 태그 저장 후 개인화, 노출 행 수·클릭 갱신·다른 회원 클릭 무시, 탈퇴 시 익명화), `devfeed_perf`에서 API 측정

## 의견

### server (1차)
- pm 확인 요청: 1번 가중치·반감기, 2번 점수 비율, 5번 콜드 스타트에 조회수 0 포함 여부, 7번 `algorithm` 이름
- dba 확인 요청: 2번 후보 조회 방식, 7번 노출 INSERT량(페이지당 20행)과 클릭 UPDATE의 인덱스(`uk_rec_impressions_request_post`), 8번 배치
- client 확인 요청: 6번 스냅샷 만료 시 `INVALID_CURSOR` 처리, 4번 이유 개수(1~2개)
- 합의되면 구현 계획을 사용자에게 승인받고 착수함

### pm (1차)
- 1번 선호도: 승인. 관심 3.0 / 북마크 2.0 / 읽기 1.0, 반감기 7일. 명시적 신호(관심·북마크)가 암묵적 신호(읽기)보다 강해야 한다는 기획 의도와 맞음
- 2번 점수: 비율 0.7 / 0.2 / 0.1 승인. 단 두 가지 보완 요청
  - **후보에서 북마크한 글도 제외**: 이미 저장한 글은 다시 추천할 가치가 낮음 (F-042 후보 정의에 "북마크하지 않은" 추가)
  - **후보 부족 시 채움**: 선호 태그가 적어 태그 일치 후보가 20건 미만이면, 남은 자리를 콜드 스타트 규칙(최근 14일 인기순, 읽음·북마크 제외)으로 채우고 이유는 `POPULAR`. 관심 태그를 막 고른 신규 회원이 빈약한 추천 화면을 보지 않게 하기 위함. 이 경우 `fallback`은 false 유지, 노출 행 `algorithm`은 해당 카드 기준으로 기록(`TAG_V1` / `COLD_POPULAR`)
- 3번 다양성: 승인. F-042 "연속 3개 이상 금지"와 일치
- 4번 이유: 1~2개 승인 (client 의견 후 확정)
- 5번 콜드 스타트 조회수 0 포함: 승인. 008은 "인기 글" 화면의 의미 문제였고, 추천은 화면이 비지 않는 것이 우선. 정렬은 조회수 내림차순, 동점 최신순 그대로
- 6번 스냅샷: 단일 인스턴스 전제 승인. 서버 재시작 시 스냅샷 소실 → `INVALID_CURSOR` → 첫 페이지 재요청 흐름이면 충분
- 7번 `algorithm` 이름 `TAG_V1`, `COLD_POPULAR` 승인. F-043 도입 시 `TFIDF_V1` 형식으로 이어감
- 9번 목표·검증 계획 승인. 탈퇴 시 노출 행 익명화 e2e 포함 확인함
- 기획서 반영: F-042 후보 정의(북마크 제외)·부족 시 채움 규칙은 dba·client 의견 후 결정과 함께 `02-features.md`에 반영함
