### 자동 아바타
- 원 안에 닉네임 첫 글자(영문은 대문자). 배경은 닉네임에서 정해지는 무채색 계열 5~6단계 중 하나, 라이트·다크 모두 대비 4.5:1 이상
- 댓글 작성자 옆에도 같은 아바타(작게) + 등급 배지 표시 (026 댓글 영역)

### 활동 등급 (F-083)
| 레벨 | 이름 | 누적 점수 |
|---|---|---|
| Lv.1 | Hello World | 0 |
| Lv.2 | Junior Dev | 100 |
| Lv.3 | Senior Dev | 500 |
| Lv.4 | Tech Lead | 2,000 |
| Lv.5 | Architect | 5,000 |
- 이름은 023 원칙대로 영어 표기. 보안 계열 대안(Script Kiddie → Bug Hunter → Pentester → Red Teamer → White Hat)은 사용자 선택 시 교체 (이름만 바뀌므로 구현 영향 없음)

### 점수 규칙
| 활동 | 점수 | 제한·회수 |
|---|---|---|
| 글 읽기 (원문 이동, F-012) | +1 | 같은 글은 처음 1회만, 하루 최대 30점 |
| 좋아요 | +2 | 같은 글 1회만. 취소하면 회수 |
| 댓글·답글 작성 | +5 | 하루 최대 10개분(50점). 본인 삭제·관리자 숨김 시 회수, 숨김 해제 시 복구 |
| 북마크 | 0 | 수치만 표시, 점수 없음 (저장만 반복하는 어뷰징 방지) |
- 점수는 **누적 원장** 기준: 읽은 기록을 지우거나 1년 보관 만료로 기록이 사라져도 읽기 점수는 남음. 좋아요 취소·댓글 삭제처럼 활동 자체를 되돌린 경우만 회수
- 회수로 점수가 내려가면 등급도 내려감 (최저 Lv.1, 점수 음수 없음)
- 기존 회원: 도입 시 현재 읽은 기록·좋아요·보이는 댓글로 초기 점수 계산 (하루 제한은 초기 계산에 적용 안 함)
- "등급 안내" 클릭 → 작은 모달로 위 두 표 표시 (해요체)
- 탈퇴(F-032): 점수·원장 삭제

### 수치 기준
- 좋아요 = 지금 좋아요 중인 글 수, 댓글 = 보이는 댓글+답글 수(삭제·숨김 제외), 읽은 글 = 읽은 기록 현재 개수, 북마크 = 북마크 현재 개수
- 본인 화면은 활동 직후 바로 반영(낙관적 갱신 또는 재조회), 최대 지연 없음

- 회원: 4개 탭·검색 좌측 맨 위에 카드, 수치가 실제 행 수와 일치, 활동 직후 반영

## 의견

### server (1차) — 조회·쓰기 경로 관점 의견 (dba 스키마 전)
**1. 원장 형태 제안 (dba)**
- `score_events`: `user_id`, `kind` ENUM('READ','LIKE','COMMENT'), `ref_id`(READ·LIKE = post_id, COMMENT = comment_id), `points`(실제 적립한 점수, 하루 제한에 걸리면 0), `revoked_at` NULL, `created_at`
  - UNIQUE `(user_id, kind, ref_id)` → 같은 글 재읽기·동시 중복 요청이 키 하나로 막힘 (`INSERT IGNORE` 영향 행 1일 때만 점수 반영)
  - 인덱스 `(user_id, kind, created_at)` → 하루 제한 합계
- `users.score` INT UNSIGNED 카운터(CHECK ≥ 0). 원장 변경과 같은 트랜잭션에서 증감. 프로필·댓글 작성자 등급은 이 컬럼만 읽음
- 등급(레벨·이름·기준 점수)은 저장하지 않고 server 상수로 계산 → 이름 교체(보안 계열 대안)가 코드 상수만 바꾸면 끝남

**2. 회수·복구 규칙 (pm 확인 바람)**
- 좋아요 취소: 원장 행 **삭제** + 점수 회수 → 다시 좋아요하면 다시 +2 (켜고 끄기 반복은 순증 0이라 어뷰징 아님)
- 댓글 본인 삭제: 행 유지 + `revoked_at` 설정 + 회수. 관리자 숨김도 같음, 숨김 해제는 `revoked_at` NULL + 복구
- **하루 제한은 회수된 행도 셈**: 댓글 10개 쓰고 지우고 다시 쓰기로 50점 넘게 받는 것을 막음. 즉 "하루 10개분"은 "하루 처음 10개 작성"
- 읽기: 하루 30점 넘은 뒤 처음 읽은 글은 0점 행이 남아 그 글은 나중에 읽어도 0점 ("같은 글 처음 1회" 해석). 다른 해석(다음 날 다시 읽으면 +1)을 원하면 0점 행을 남기지 않는 방식으로 바꿈
- 하루 경계: **KST 자정** 기준 (서비스 사용자 기준). 원장 `created_at`은 UTC 저장, 범위 계산만 KST

**3. 동시성·잠금 순서**
- 하루 제한 합계와 적립을 원자적으로 하려면 회원 행 `FOR UPDATE`가 필요. 댓글 작성은 이미 회원 행을 먼저 잠금(026)
- **좋아요는 지금 글 행을 먼저 잠그므로 점수 갱신(회원 행)을 뒤에 붙이면 댓글 작성(회원 → 글)과 순서가 반대가 됨** → 같은 회원이 같은 글에 좋아요·댓글 동시 요청 시 데드락 가능. 좋아요도 회원 행 → 글 행 순서로 바꿈 (server 내부 변경, `reactions.sql` 잠금 순서 갱신 필요 → dba)
- 조회(F-012)는 회원만 적립. 회원 행 잠금이 추가되지만 같은 회원의 동시 조회는 드물어 경합 작음

**4. API 초안 (명세는 스키마 확정 후)**
- `GET /me/profile` (회원) → `{ nickname, score, grade: { level, name, minScore, nextMinScore | null }, stats: { likes, comments, reads, bookmarks } }`
  - 수치는 카운터 없이 `COUNT`: `post_likes` PK·`read_histories` PK·`bookmarks` PK 범위, 댓글은 `idx_comments_user_created` 범위 + `status = 'VISIBLE'`. 회원당 수천 행 이하라 4개 합쳐 수 ms 예상 → 측정 후 기준(300ms) 확인
  - 아바타는 닉네임으로 client가 계산 → 응답에 필드 없음
- 댓글 응답 `author`에 `grade: { level, name }` 추가 (목록 조회에 `users.score` 컬럼 하나 더 읽음, 추가 쿼리 없음)
- 활동 직후 반영: 좋아요·댓글·조회 응답은 바꾸지 않고 client가 `GET /me/profile` 재조회 (응답 형태 변경 최소화). client가 응답에 점수 포함을 원하면 의견 바람
- 등급 안내 모달 표는 client 상수 (spec 표 그대로). server 상수와 어긋나지 않게 단위 테스트로 spec 값 고정
- 탈퇴: 원장 FK CASCADE면 server 추가 작업 없음 (`users.score`는 회원 행과 같이 삭제)
- 초기 점수 백필은 dba 쿼리로 원장 생성 → `users.score = SUM(points)`. 백필 후 정합성 검사(`users.score` = 원장 미회수 합계) 쿼리도 부탁

### pm (server 1차 결정, 2026-11-22)
- 원장 `score_events` + `users.score` 카운터 + 등급은 server 상수 계산: 승인 (dba 스키마에서 확정)
- 해석 3건
  1. 좋아요 취소 = 원장 행 삭제·회수, 다시 누르면 다시 +2: **승인** (반복해도 순증 0)
  2. 하루 제한은 회수된 행도 셈 ("하루 처음 10개 작성"): **승인**. 댓글 삭제 후 재작성으로 한도 우회 방지
  3. 읽기 하루 30점 초과분: **0점 행을 남기지 않음**으로 결정 (server 제안의 대안). 한도에 걸린 글은 다음 날 처음 읽을 때 +1 받을 수 있음. 한도가 이미 하루 상한이라 어뷰징 여지 없고, "오늘 많이 읽으면 그 글은 영원히 0점"이 되는 불이익을 없앰
- 하루 경계 KST 자정, 저장은 UTC: 승인
- 잠금 순서: 좋아요도 **회원 행 → 글 행**으로 변경 승인 (댓글 작성과 같은 순서). dba는 `reactions.sql` 잠금 순서 갱신
- API: `GET /me/profile` 형태·댓글 `author.grade` 승인. 활동 직후 반영은 client가 `GET /me/profile` 재조회 방식으로 (응답 형태 변경 없음)
- 등급 표는 client 상수·server 상수 모두 spec 값과 단위 테스트로 고정
- 다음: dba 스키마(백필·정합성 검사 포함) → server 명세

### dba (1차) — 스키마 `0014`·규칙 SQL·백필·측정 (pm 결정 기준)
- `db/migrations/0014_create_score_events.sql`, 쿼리 `db/queries/score.sql`
  | 대상 | 내용 |
  |---|---|
  | `users` | `score INT UNSIGNED NOT NULL DEFAULT 0` (`INSTANT`) |
  | `score_events` | PK `(user_id, kind, ref_id)`, `kind` READ·LIKE·COMMENT·ARCHIVE, `points INT UNSIGNED`, `created_at`, `revoked_at`(COMMENT만 CHECK), 인덱스 `(user_id, kind, created_at)`, FK CASCADE |
- server 1차와 다른 점
  - UNIQUE 대신 **PK로 씀** (별도 id 없음). 행당 크기가 줄고 회원 범위 조회가 클러스터드 순서라 빠름
  - `ARCHIVE` 값 추가 (아래 보관 제안용. 채택 안 되면 쓰지 않음)
  - 읽기 초과분 행 없음 (pm 결정). 댓글 11번째부터는 0점 행 남김 (회수 판단·한도 계산 일관)
- 잠금 순서 갱신: `reactions.sql` 좋아요 켜기·끄기 첫 단계에 회원 행 `FOR UPDATE` 추가 (회원 → 글 → 부모 댓글 → 댓글 → 원장)
- 점수 증감은 **원장 쓰기의 영향 행 수로만** 판단 바람. `SELECT points INTO @p`는 행이 없으면 변수가 이전 값으로 남음 (시험 중 확인)
- 백필: server가 원장 쓰기를 시작한 **직후** dba가 1회 실행 (`INSERT IGNORE`라 겹쳐도 안전). 성능 DB 255만 행 22초 → 운영 규모는 즉시
- 정합성 검사 6항목 (`score.sql` 끝): `users.score` = 미회수 합, 원장 없는 좋아요·좋아요 없는 원장, 댓글 상태와 회수 일치, 지워진 댓글 미회수, 원장 없는 댓글 → e2e·운영 점검에 사용
- 탈퇴: 원장 FK CASCADE, `withdrawal-check.sql`에 `score_events` 추가 (12개 테이블)
- 검증
